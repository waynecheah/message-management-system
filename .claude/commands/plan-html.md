Generate a single standalone HTML file directly from a markdown spec — no CLI, no API calls, no framework. Just one self-contained `.html` file (inline `<style>`, no external build step) written next to the source markdown.

**Usage**: `/plan-html <path-to-markdown-spec>`

**Example**: `/plan-html docs/superpowers/specs/2026-05-25-auth-mvp-design.md`

The path may be relative to the repo root or absolute.

---

## What you will do

Read the source markdown, then write one HTML file with the same basename in the same directory.

### Step 1 — Resolve paths

- Input spec: `$ARGUMENTS` (absolute, or relative to the current working directory / repo root)
- Slug: basename of input without `.md`
- Output HTML: same directory as the input, `<slug>.html`

### Step 2 — Read the source markdown

Read the full file at `$ARGUMENTS`.

### Step 3 — Extract the header fields

From the markdown content (title/frontmatter/first heading, or infer sensibly if absent):

| Field | Source |
|---|---|
| `title` | The document's main heading, or filename if none |
| `date` | Frontmatter/first mentioned date, else today's date — format like `May 13, 2026` |
| `status` | One of `Draft`, `Approved`, `Superseded`, `Implemented` — infer from content, default `Draft` |
| `description` | 1–3 sentence plain-text summary of what the spec is about |
| `tags` | 3–8 lowercase kebab-case tags inferred from the content |

### Step 4 — Map content into sections

Only include a section if the source markdown actually has matching content — never emit an empty or filler section. Use this fixed set, in this order:

1. **Overview** — high-level summary / intro paragraph(s), if distinct from the description
2. **Goals / Scope and Non-Goals** — what's in scope, what's explicitly out of scope for this phase (not the final "Out of Scope (MVP)" section — see below)
3. **Key Decisions** — the locked/selected decisions, approach comparisons, rejected alternatives
4. **Architecture** — module layout, component structure, data flow
5. **Data Model** — tables, schemas, entities
6. **API Design** — endpoints, request/response shapes, contracts
7. **Testing Strategy** — test layers, coverage plan
8. **Out of Scope (MVP)** — explicit non-goals/deferred work for this MVP/phase
9. **Open Questions** — unresolved questions, follow-ups

Map the source markdown's actual headings onto these buckets by meaning, not by exact title match (e.g. a source section called "Non-Goals" or "What's out" maps to "Out of Scope (MVP)"). Preserve all substantive content — tables, code identifiers, lists — do not summarize it away.

### Step 5 — Write the HTML file

Write a single self-contained HTML document (`<!doctype html>` through `</html>`) to `<same-dir-as-source>/<slug>.html`, following this structure:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>{{title}}</title>
  <style>/* see below */</style>
</head>
<body>
<div class="spec-shell">

  <header class="spec-header">
    <div class="spec-meta">{{date}}</div>
    <h1 class="spec-title">{{title}}</h1>
    <p class="spec-description">{{description}}</p>
    <div class="spec-status"><span class="spec-badge spec-badge--{{status-lowercase}}">Status: {{status}}</span></div>
    <div class="spec-tags"><span class="spec-tag">#tag</span>...</div>
    <div class="spec-source">
      <a href="{{relative-path-to-source-md}}">View source markdown ↗</a>
      <span class="spec-source-meta">generated by <code>claude</code></span>
    </div>
  </header>

  <div class="spec-columns">
  <main class="spec-page">

    <section class="spec-section" id="overview">
      <h2>Overview</h2>
      <h3 id="overview-context">...</h3>
    </section>
    <!-- one section per applicable bucket from Step 4, each in its own <section class="spec-section" id="kebab-slug"> -->

  </main>

  <aside class="spec-toc" aria-labelledby="spec-toc-title">
    <nav>
      <p class="spec-toc-title" id="spec-toc-title">On this page</p>
      <ul>
        <li><a href="#overview">Overview</a>
          <ul>
            <li><a href="#overview-context">...</a></li>
          </ul>
        </li>
        <!-- one top-level <li> per section, one nested <li> per <h3> in that section -->
      </ul>
    </nav>
  </aside>

  </div>
</div>

<script>/* see "The sidebar highlights the section in view" below */</script>
</body>
</html>
```

Content rules inside sections:
- Headings: `<h2>` for section title (inside the `<section>`), `<h3>` for subheadings within a section
- **Every `<h3>` carries a stable kebab-case `id`**, prefixed by its section (`kd-build-slices`, `api-create-path`, `test-unit`). The sidebar links to these ids, so a heading without an id is a broken sidebar entry.
- Paragraphs, `<ul>`/`<ol>`, and `<table>` render with plain semantic HTML — style them generically in the shared `<style>` block, no per-instance inline styles
- Decision/callout text (e.g. "Decision:", "Why X?") → `<div class="spec-callout">` with a `<strong>` lead-in
- Comparison options (selected vs rejected approaches) → a simple `<div class="spec-compare">` grid of `<div class="spec-compare-item">` blocks, each optionally tagged `spec-compare-item--selected` or `spec-compare-item--rejected`
- Diagrams: only include if the source has them, and **draw them with inline HTML and CSS — never Mermaid, never a CDN**. A linear flow becomes `<figure class="spec-figure">` with a `<figcaption>` and an `<ol class="flow">` of `<li class="flow-step">` items, each holding a `<span class="flow-node"><b>Name</b><em>detail</em></span>`. Draw the connectors as CSS pseudo-elements with `content: ""`, so no arrow glyph is announced to a screen reader. Mark an external system with `flow-node--infra` and the entry/exit points with `flow-node--io`. An ordered list conveys the sequence semantically, which reads better than a generated SVG.
- No JS framework, no build step, no external CSS, no external script — everything needed to view the page must be in this one file. One small inline `<script>` is required, for the sidebar highlight below — it is the only script the page carries, and it has no `src` attribute and calls no network resource

### The sidebar is required

Every generated page carries a sticky "On this page" sidebar in a right-hand column. Build it from the sections you actually emitted in Step 4:

- One top-level entry per `<section class="spec-section">`, linking to its `id`
- One nested entry per `<h3>` inside that section, linking to the `<h3>` id
- Shorten a nested label when the heading is long, but keep it recognisable — `Integration tests — compose stack, Nest testing module, supertest` becomes `Integration tests`
- The header block spans the full width above both columns. The sidebar starts beside the first section
- Under 1080px the sidebar moves above the content as a bordered card with a two-column list. Under 620px that list becomes one column
- Never emit an entry for a section you did not write, and never write a section with no entry

### The sidebar highlights the section in view

The sidebar link for the section on screen carries an `is-active` class. This
needs one inline script — plain JavaScript, no dependency, no network call.
Place it right before `</body>`, after the closing `</div>` of `.spec-columns`:

```html
<script>
(function () {
  var tocLinks = Array.prototype.slice.call(document.querySelectorAll('.spec-toc a[href^="#"]'));
  var targets = tocLinks
    .map(function (a) {
      var el = document.getElementById(a.getAttribute('href').slice(1));
      return el ? { link: a, el: el } : null;
    })
    .filter(Boolean);

  if (!targets.length) return;

  var current = null;
  var ticking = false;
  var activationLine = 120;

  function topLinkFor(link) {
    var li = link.closest('li');
    var maybeTopLi = li.parentElement.parentElement;
    return maybeTopLi && maybeTopLi.tagName === 'LI' ? maybeTopLi.querySelector('a') : null;
  }

  function setActive(link) {
    if (current === link) return;
    tocLinks.forEach(function (a) { a.classList.remove('is-active'); });
    link.classList.add('is-active');
    var topLink = topLinkFor(link);
    if (topLink) topLink.classList.add('is-active');
    current = link;
  }

  function update() {
    ticking = false;
    var active = targets[0];
    for (var i = 0; i < targets.length; i++) {
      if (targets[i].el.getBoundingClientRect().top - activationLine <= 0) {
        active = targets[i];
      } else {
        break;
      }
    }
    setActive(active.link);
  }

  function onScroll() {
    if (ticking) return;
    ticking = true;
    window.requestAnimationFrame(update);
  }

  window.addEventListener('scroll', onScroll, { passive: true });
  window.addEventListener('resize', onScroll);
  update();
})();
</script>
```

It walks the sidebar links in document order, finds the last section (or
subsection) whose top has crossed 120px from the viewport top, and marks that
link — and its top-level ancestor, if it has one — with `is-active`. Use this
script verbatim; do not invent a different scroll-spy approach. It depends on
the exact sidebar nesting from the skeleton above (`<li><a>…</a><ul>…</ul></li>`
for a section with subheadings) — do not restructure the sidebar markup without
updating `topLinkFor` to match.

**Shared `<style>` block** — write CSS matching this visual language (light theme, generous whitespace, small-caps meta text, pill badges/tags, left-border callouts, clean tables):
- `.spec-shell`: centered, `max-width: 1120px`, comfortable padding, system font stack
- `.spec-columns`: CSS grid, `minmax(0, 1fr) 236px`, `gap: 56px`, `align-items: start`
- `.spec-page`: the content column, `max-width: 760px`, `min-width: 0`
- `.spec-toc`: `position: sticky`, `top: 32px`, `margin-top: 58px` to align with the first section, `max-height: calc(100vh - 64px)` with `overflow-y: auto` so a long list scrolls on its own
- `.spec-toc-title`: 11px, uppercase, wide letter-spacing, muted
- `.spec-toc` links: no bullets, no underline, block-level, 13px. Top-level links take the body ink colour; nested links are 12.5px and muted, in a `<ul>` with a left border and `padding-left: 14px`. Hover and `:focus-visible` turn accent-coloured and underlined
- `.spec-toc a.is-active`: accent colour, heavier weight (this is the section the script marks as in view — see below)
- `.spec-section, .spec-section h3`: `scroll-margin-top: 24px`, so an anchor jump does not sit flush against the viewport top
- `.spec-header`: full width, `border-bottom: 1px solid` the rule colour; cap its children at `max-width: 760px` so the title and description stay readable while the divider spans both columns
- `.spec-meta`: small, muted gray, uppercase-ish date line
- `.spec-title`: large bold heading
- `.spec-description`: muted gray paragraph, slightly larger line-height
- `.spec-badge`: pill with padding + border-radius, green-tinted for Approved, gray for Draft, amber for Superseded, blue for Implemented
- `.spec-tag`: small pill, light gray background, muted text
- `.spec-source`: small muted line with a link and separator dot
- `.spec-section`: vertical rhythm spacing between sections, `h2` with a bottom border
- `.spec-callout`: light background, colored left border (~3-4px), padding, rounded corners
- `.spec-compare` / `.spec-compare-item`: CSS grid (responsive, wraps on narrow viewports), bordered cards, selected variant gets a highlighted border/background, rejected variant gets a muted badge
- `table`: full-width, bordered rows, muted header row, comfortable cell padding
- `code`: monospace, subtle background pill
- `.spec-figure` / `.flow` / `.flow-node`: bordered figure box, centred caption, a stack of bordered nodes joined by CSS connectors

### Step 6 — Check the writing style

Before you report, read back the prose you wrote and correct any breach of the
writing style section:

- Any sentence longer than 25 words (20 for an instruction)
- Any paragraph longer than six sentences
- Any passive voice with a known actor
- Any perfect tense, or any `-ing` form used as a noun or clause opener
- Any concept named by two different words
- Any noun cluster longer than three words

### Step 7 — Verify the file

Run these two checks and report the result. Do not skip them.

1. **No external asset.** Search the file for `http://` and `https://`. Both must return no match. Search for `<link`. It must return no match. Search for `<script`. It must return **exactly one** match — the inline sidebar-highlight script — and that tag must carry no `src` attribute.
2. **No broken anchor.** Collect every `href="#..."` and every `id="..."`. Every sidebar link must resolve to an id in the page. Every section id and `<h3>` id must appear once in the sidebar.

### Step 8 — Confirm

Report:
- File written (path)
- Slug, title, status, date
- Which of the 9 sections were included vs omitted (and why, briefly, if a source section didn't fit any bucket)
- The result of both checks in Step 7

## Writing style — ASD-STE100 Simplified Technical English

Write all prose in the generated HTML in Simplified Technical English (ASD-STE100).
The goal is a page that one reader understands one way only — no second reading,
no ambiguity, no decoding.

### Sentences

- **Descriptive sentences: 25 words maximum.**
- **Instruction sentences: 20 words maximum.**
- One idea per sentence. Split a long sentence; do not add a comma.
- Put the main topic first. Do not open with a subordinate clause.

### Paragraphs

- Six sentences maximum.
- One topic per paragraph.
- State the point in the first sentence.

### Verbs

- Use the active voice. Use the passive only when the actor is unknown or does not matter.
- Use simple tenses only: present, past, future.
  Do not use perfect tenses — write "we chose X", not "X has been chosen".
- Do not use `-ing` forms as nouns or to open a clause.
  Write "We use X to reduce cost", not "Using X reduces cost".
- Use the imperative for instructions: "Run the tests."

### Words

- **One word, one meaning.** Choose one term for each concept and repeat it
  everywhere. Never vary a term for style — a synonym reads as a new concept.
  Where the repo defines a term (`CONTEXT.md`), that term wins.
- Prefer short, common words. Write "use", not "utilise"; "start", not "initiate".
- No idioms, metaphors, slang, or humour.
- Keep the articles: "the", "a", "an". Do not write in telegraphic style.
- Keep "that" when it helps the reader parse the sentence.
- Noun clusters: three words maximum. Break a longer cluster with a preposition —
  write "the index for the search backend", not "the search backend index config".

### Structure

- Write sequential steps as a numbered list.
- Put a warning before the action it applies to, never after.
- Write positively. Avoid double negatives.

### Exempt from these rules — keep verbatim

- Identifiers, code, endpoints, schemas, field names, file paths, and values
- Table cells that hold data
- Direct quotations from the source markdown

### Example

Before:

> Having weighed the trade-offs involved, it was ultimately decided that keyset
> pagination would be adopted, given that the performance of skip-based
> pagination tends to degrade as the offset grows larger.

After:

> We use keyset pagination. Skip-based pagination becomes slower as the offset increases.

The rewrite removes the `-ing` opener, the passive voice, the perfect tense, and
the hedging. Two short sentences replace one long sentence.

### Known limitation

Full ASD-STE100 compliance requires the approved dictionary of about 900 words,
which is not bundled here. Apply the writing rules above exactly. Approximate the
dictionary by choosing the most common, most concrete word available.

## Key rules (non-negotiable)

1. **Single output file, and nothing loaded from the network.** No JSON, no search index, no companion asset, no CDN import, no font link, no Mermaid. The page must render with the machine offline. The one exception is the inline sidebar-highlight `<script>` from Step 5 — it has no `src` and calls no network resource. This is verified in Step 7.
2. No Astro, no component catalog, no build step — write plain HTML/CSS by hand.
3. Only emit a section from the fixed list in Step 4 if the source markdown has matching content — never pad with empty sections.
   **Every emitted section appears in the sidebar, and every sidebar entry points at an emitted section.**
4. Do not invent content not present in the source markdown. Preserve identifiers, code, table data, and technical details verbatim (exact names, values, endpoints, schemas, numbers stay exact).
5. **Write for a human reader, not a markdown-to-HTML converter.** The whole point of this page is that someone can understand the spec *without* reading the source markdown. Do not copy or lightly reformat the source prose. Rewrite every section in Simplified Technical English — see the writing style section above, and apply it in full. Cut hedging, repetition, and meta-commentary from the original document. Only technical facts (identifiers, values, schemas, code) stay verbatim. Everything else reads as a clear explanation of the spec, not a translation of it.
6. If the source markdown is unreadable or has no discernible title/content, write nothing and explain why.
