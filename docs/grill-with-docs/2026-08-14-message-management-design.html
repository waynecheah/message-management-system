Grill Decision Review — Message Management System

This document records the grill session on the build design. The session asked nineteen questions. Each question closed one open point in the design. This document holds one card for each decision.

Write-back status

The session wrote every decision back to the draft source. The source file above is current. It is the single record of the build design. This review explains why each decision holds. It does not replace the source.

The session also generated the plan HTML from that source after the write-back. The plan HTML therefore shows the settled design and not the original draft.

The session changed documents only. No implementation code exists yet. The repository holds documents, a package.json, a tsconfig.json and a lockfile. No source file under src/ was created or altered.

Assumptions

  1. The timebox is four to five hours, as CONTEXT.md states.
  2. The target toolchain is nub 0.6.0 on Node 24.12. The probes ran on that pair.
  3. MongoDB, Kafka and Elasticsearch run through docker-compose on the reviewer's machine.
  4. The README is the graded deliverable. Every trade-off must appear there with its reason.
  5. An external identity provider issues the tokens. This service verifies them and never mints one.
  6. The reviewer runs one command to start the system and one command to run the tests.

Execution assumption. The required local gateway at 127.0.0.1:8787 was unavailable. The run used the authenticated Claude endpoint instead. This affected the transport of the session only. It changed no design decision, no recommendation and no written file.

Decisions

The cards follow the order of the session. Each card holds the same five parts in the same order: the numbered question, the question asked, why it mattered, the decision, and the practical effect. Some cards add the rejected options and the evidence.

01

How does slice 0 create the skeleton?

Toolchain
Question asked

Slice 0 said "restructured nest new". The repository tsconfig cannot run a decorator, and nub cannot drive the Nest scaffolder. How should slice 0 build the skeleton?

Why it mattered

This blocked every later slice. nub rejects Stage 3 decorators, because the oxc transpiler does not support them. The repository tsconfig set neither decorator flag, so NestJS could not start at all. The design document never mentioned tsconfig.

Decision

Write the skeleton by hand. Never run nest new. Slice 0 adds experimentalDecorators and emitDecoratorMetadata to tsconfig.json. It keeps ESM and verbatimModuleSyntax. It installs the Nest packages with nub add, then creates main.ts and app.module.ts directly in the four layers.

Practical effect

The application starts. The layer directories exist from the first commit. No generated file needs a later move. ADR-0005 gained a dated amendment, because its earlier text allowed nest new for the initial skeleton.

Rejected
  • Run nest new, then correct it. The scaffolder picks its own package manager and writes npm scripts, which ADR-0003 forbids. It also writes the flat feature shape that ADR-0005 calls a trap.
  • Drop ESM for CommonJS. The probe showed ESM works, so the change bought nothing.
  • Defer the decision. The blocker stops slice 0 on the first run.
Evidence — probe output
$ nub probe.ts
Error: Nub: Stage 3 decorators are not supported by the transpiler yet.
This is an upstream limitation in oxc (oxc-project/oxc#9170).
Workarounds:
  1. Set "experimentalDecorators": true in tsconfig.json ...

$ nub probe.ts        # after both flags set
decorator ran, class: Svc
emitted metadata: ["design:paramtypes"]

$ nub probe2.ts       # ESM + verbatimModuleSyntax
ESM + verbatimModuleSyntax ok, class: Svc
paramtypes: [ [ 'design:paramtypes', [ 'Dep' ] ] ]
02

Which TypeScript version does the project use?

Toolchain
Question asked

package.json pinned typescript: ^7. Version 7 is the native tsgo compiler, and ts-jest targets the 5.x compiler API. What happens to the test toolchain?

Why it mattered

Three tools read the TypeScript compiler API: ts-jest, typescript-eslint and the type check. All three could break at once. The timebox is four to five hours, so a broken toolchain costs the graded core.

Decision

Pin TypeScript to ^5.9.

Practical effect

nub transpiles at run time, so TypeScript here serves only the type check, the lint and ts-jest. Version 7 adds no value to this project. The whole Nest and Jest stack now runs on the version it was tested against.

Rejected
  • Keep version 7 and use @swc/jest. It adds one dependency and loses type errors inside tests.
  • Keep version 7 and probe first. It spends timebox on a risk with no upside.
03

What happens to the Swagger CLI plugin?

Toolchain
Question asked

The Swagger CLI plugin cannot run under nub. ADR-0019 accepted @nestjs/swagger because that plugin removed the objection about @ApiProperty on every field. What now?

Why it mattered

The plugin is a TypeScript transformer. The Nest CLI applies it during nest build or nest start through nest-cli.json. Decision 01 removed the Nest CLI from the project. The transform layer of nub uses oxc and exposes no transformer hook. The central justification of ADR-0019 therefore failed.

Decision

Keep @nestjs/swagger. Write @ApiProperty and @ApiPropertyOptional by hand on the four DTOs.

Practical effect

The setup cost moves from near zero to about fifteen minutes. The surface stays small: three endpoints, four DTOs, no nested request model. ADR-0019 already carries a rule for this case. A disabled plugin needs an explanation in the README, so the README must state it. ADR-0019 gained a dated amendment.

Rejected
  • Drop Swagger. ADR-0019 calls it the first item to cut under time pressure, but the reviewer value stays real for one package.
  • Add a build step for the docs. It restores a build pipeline that ADR-0003 removed on purpose, for an ungraded artefact.
Evidence

The nub runtime directory holds transform-core.mjs and no plugin API. The nub command list holds no build or transform subcommand.

04

Which component enters the AsyncLocalStorage store?

Runtime
Question asked

The design drew this order: JwtAuthGuard, then ALS.run({ tenantId, senderId }), then ValidationPipe. Which component performs the run call?

Why it mattered

No component in the design could do it. A guard returns a boolean, so an als.run(cb) inside canActivate closes as soon as the guard returns. ADR-0012 named middleware, but Nest runs middleware before guards, so the token is still unverified there. The order in the diagram was correct and unbuildable.

Decision

Use a global APP_INTERCEPTOR. It reads request.user, which the passport strategy sets, and it wraps next.handle() in als.run().

Practical effect

Nest runs interceptors after guards and before pipes. The pipes, the handler, the use case and the repository therefore all run inside the store. The @Public() health route carries no user, so the interceptor enters no store, and a later require() throws. That is the intended fail-closed behaviour. ADR-0012 gained a dated amendment for the placement and for the port name IdentityContext.

Rejected
  • als.enterWith() in the guard. One line shorter. It binds the store to the rest of the async resource instead of a bounded callback, so the store can leak across requests.
  • Pass identity explicitly from the controller. It contradicts ADR-0012 and the good pattern in ADR-0018.
05

What do the read ports return?

Layering
Question asked

Message has a private constructor, and Message.create() generates the id and the timestamp. The ports declared Page<Message> and Message[]. How does a read path build those values?

Why it mattered

A stored message already has an id and a timestamp, so create() cannot rebuild it. The design also decided to return the Elasticsearch hit directly. An Elasticsearch hit is a derived value and can be stale. A domain entity built from that hit claims a status the value does not hold.

Decision

Read ports return MessageView. It is a plain immutable type with no behaviour. MessageWriter.save is the only port that takes the entity.

Practical effect

The entity stays on the write path, where its one invariant lives. The Elasticsearch adapter maps a hit straight to a view with no entity construction. Fakes for the read ports become trivial. The session created ADR-0020 for this decision and added it to the ADR index.

Rejected
  • Add Message.restore(props). One type instead of two. It adds a public constructor that trusts its input and skips the invariant, and any caller can reach it.
  • Return raw documents. It leaks _id and the index shape upward.
06

Where does the cursor id become a BSON Binary?

Persistence
Question asked

ADR-0008 states that the mapper is the single place for the translation between _id and id. The keyset filter needs a BSON UUID built from the cursor string. Where does that conversion live?

Why it mattered

The repository would become a second translation site. That breaks a rule that a reader can check at a glance. The rule protects one thing: only one file knows how the id is represented.

Decision

The mapper owns both directions. It exports toBinaryId and toStringId. The repository calls them for the keyset bound.

Practical effect

The repository still names _id in the filter and the sort, which is unavoidable. It never knows the representation. The rule in ADR-0008 stays literally true, and no new abstraction appears.

Rejected
  • A MessageId codec module. It is a value object with no invariant to protect, which ADR-0016 names as invented ceremony.
  • Widen the rule to "one module". It weakens a rule that is currently checkable at a glance.
Evidence — why the tiebreaker is correct

MongoDB orders BinData by length, then by subtype, then byte by byte. Every message _id is 16 bytes of subtype 4, so the comparison is byte-wise. A UUIDv7 leads with a 48-bit timestamp in big-endian order, so byte order equals time order. That order matches the canonical string order the cursor carries. The design now carries a test for this fact.

07

Where does a search result get its id?

Search
Question asked

The Elasticsearch mapping listed tenantId, conversationId, senderId, timestamp, content and metadata. It held no id. Every hit needs one. Should the mapping also become stricter?

Why it mattered

Decision 05 made search return a MessageView, and that view carries an id. The gap would have appeared at run time in slice 5. A strict mapping also closes the failure that metadata already guards against.

Decision

Take the id from hit._id. Add "dynamic": "strict" at the root of the mapping. Store no id field.

Practical effect

ADR-0011 already makes the document id the message id, so a copy in _source would be a second value that nothing keeps in step. The adapter composes { id: h._id, ...h._source }. An unexpected top-level field now raises a hard error instead of a quiet mapping change. Strictness does not reach inside metadata, because enabled: false means Elasticsearch never parses the content.

Rejected
  • Store id as an unindexed keyword. It duplicates a value that nothing keeps in sync.
  • Store id as an indexed keyword. It pays index cost for a field nothing queries.
08

Do the content bounds measure the raw value or the sanitized value?

Boundary
Question asked

The design ran sanitize-html in a class-transformer @Transform on the DTO. Does @MaxLength(4000) then apply to what the client sent, or to what sanitization produced?

Why it mattered

ValidationPipe calls plainToInstance before it validates, so a @Transform runs ahead of every validator. That order caused two faults. sanitize-html escapes text entities, so a valid 4000-character message of ampersands grows to about 20 000 characters and gets rejected for a length the client never sent. The blank check in Message.create also became unreachable over HTTP, because the DTO always caught the case first.

Decision

Validate the raw value first. Sanitize afterwards, in a SanitizeContentPipe registered after ValidationPipe. Cap the JSON body at 256 KB.

Practical effect

The client contract now describes what the client sent. Content that sanitizes away to nothing reaches Message.create and fails there. The entity invariant becomes load-bearing instead of decorative. The body cap stops sanitize-html from parsing a megabyte.

Rejected
  • Keep @Transform and bound the output. One fewer moving part. It measures the wrong string and hides the entity invariant.
  • Transform, then bound both values. It creates two length rules with different meanings and a confusing error surface.
09

What makes a halted indexer visible?

Reliability
Question asked

The design refused a dead-letter queue. It argued that a poison message which halts the indexer is a visible failure, and that a skipped message is silent data loss. What makes the halt visible?

Why it mattered

The consumer runs inside the API process. A halted consumer would leave the API at 201 while search quietly stopped. The failure would then be exactly as silent as the skip it was preferred over. The argument against the dead-letter queue depended on a property the system did not have.

Decision

The consumer records its own liveness. The health route reports it. A stopped indexer returns 503 with a degraded status and a reason.

Practical effect

The claim in the design becomes true for a few lines of code. The @Public() health route gains a purpose beyond "the process is up". The check is hand-written. @nestjs/terminus is an official Nest package, but it would be a dependency for one boolean.

Rejected
  • Exit the whole process. The crash loop is maximally visible. It costs API availability for a search-index fault and demonstrates badly.
  • Log at fatal level only. "Visible" would then mean "present in stdout".
10

Does search return an envelope or a bare array?

Contract
Question asked

The list endpoint returned { items, nextCursor }. The search endpoint returned a bare array. Should search also return an envelope?

Why it mattered

Two endpoints over one resource returned two container shapes. A reviewer notices that at once. The shape also decides whether deep paging can arrive later without a breaking change.

Decision

Search returns { items: [...] }. An empty result is 200 { items: [] }.

Practical effect

Both read endpoints now share one shape. A later search_after cursor becomes an additive change. The required edge case for an empty search result changed from 200 [] to 200 { items: [] } in the test matrix.

Rejected
  • Keep the bare array. It is honest that search carries no pagination state. It costs the shape consistency between sibling endpoints.
11

What happens on a bad limit?

Contract
Question asked

The design listed "limit out of bounds" as a test case. It never stated the behaviour. What does the API return for limit=0, limit=101 and limit=abc?

Why it mattered

A clamp and a rejection produce different clients. A clamp hides a client bug. The test case could not be written while the behaviour stayed unstated.

Decision

Return 400. Never clamp.

Practical effect

ADR-0013 says reject, not repair, so this follows the decision record. It also matches forbidNonWhitelisted, which already treats an unexpected field as an error. A client that asks for 500 and silently receives 100 gets wrong information.

Rejected
  • Clamp to the valid range. It never fails a page fetch. It hides the client bug instead of surfacing it.
12

How is metadata bounded?

Boundary
Question asked

The bounds table gave content and conversationId explicit numbers. It left metadata as "optional object". What bounds that field?

Why it mattered

MongoDB stores metadata verbatim. The Elasticsearch _source keeps it too, because enabled: false indexes nothing and stores everything. An unbounded object therefore costs twice. The design already argued that a stated number beats an implicit one.

Decision

Reject metadata whose JSON exceeds 4 KB. Keep the type Record<string, any>.

Practical effect

The field gains a stated limit like every other field. The declared type stays exactly as CONTEXT.md states it. A narrower type of primitives only would depart from the given contract, and a grader could read that as a failure to follow the spec.

Rejected
  • Bound the size and require a flat object. Stronger, and it rules out deep nesting. It narrows a type that CONTEXT.md declares verbatim.
  • Leave it to the body limit. Nothing extra to build. The limit stays implicit.
13

What is the latency budget for the publish?

Reliability
Question asked

The design said a failed publish still returns 201. It never said how long that takes. What is the budget?

Why it mattered

kafkajs defaults to five retries with exponential backoff and a 30-second send timeout. The idempotent: true flag also forces maxInFlightRequests: 1. Every POST would then take about thirty seconds and return 201 while the broker is down. That is the worst of both outcomes.

Decision

Wait for the send, but bound the wait. Set retry: { retries: 2, initialRetryTime: 100 } on the producer and timeout: 2000 on the send.

Practical effect

A broker outage costs about two seconds for each POST instead of about thirty. The save still precedes the publish, so the unit test for that order stays meaningful. The service logs a failure at error level and returns 201, because the message already sits in the system of record.

Rejected
  • Fire and forget. POST latency never depends on Kafka. It loses the save-precedes-publish order and risks an unhandled rejection.
  • Wait with the defaults. Simplest, and correct under normal conditions. It degrades every write to a 30-second call during an outage.
14

Is a Sender the same thing as the authenticated principal?

Language
Question asked

CONTEXT.md defined Message, Conversation, Tenant, Message-created event, Search index and Primary store. It did not define Sender. Is Sender the authenticated principal, or a separate role that coincides with it today?

Why it mattered

The design binds senderId to the sub claim. That binding carries a domain consequence that nothing had stated. The API cannot record a message for anyone but the caller.

Decision

Sender and the authenticated principal are one concept. CONTEXT.md now defines Sender and states the consequence.

Practical effect

Transcript import, system messages and bot-relayed messages are impossible by construction, not merely unbuilt. That limit is now a recorded boundary instead of a later surprise. ADR-0016 forbids a distinction with no invariant behind it, and the source spec holds no visitor role and no agent role.

Rejected
  • Treat them as distinct concepts that coincide today. It leaves room for a visitor and agent split. It models a difference that neither the spec nor the code makes.
15

How do domain errors map to HTTP statuses?

Contract
Question asked

The module map listed domain-exception.filter.ts with the note "DomainError to HTTP status". The design never gave the mapping. What is it?

Why it mattered

The filter cannot be written without the table. One choice is load-bearing. An absent identity context could look like an authentication failure, and a wrong status sends the caller to check a token that was correct.

Decision

Return 400 for client faults and 500 for everything else.

BlankContentError      -> 400
InvalidCursorError     -> 400   (malformed base64 or shape)
CursorDirectionError   -> 400   (desc cursor with sort=asc)
MissingIdentityError   -> 500   (the guard should have prevented it)
anything else          -> 500   (logged, message not echoed)
Practical effect

A client sees one status for one class of problem, whichever layer caught it. An absent identity context is deliberately not a 401, because the guard already ran and the case means a bug in our wiring.

Rejected
  • Use 422 for semantic faults. More precise HTTP. It gives two statuses for what a client experiences as one problem.
16

What does a cross-tenant read return?

Security
Question asked

The test matrix required a case: tenant B must not read tenant A's conversation. It never stated the expected response. What comes back?

Why it mattered

A 404 and an empty page leak different amounts of information. Tenant isolation exists to withhold exactly this kind of fact.

Decision

Return 200 { "items": [], "nextCursor": null }.

Practical effect

The tenant filter is part of the query, so the conversation does not exist from that caller's view. The response is identical to a conversationId that never existed. Nothing is special-cased and nothing leaks.

Rejected
  • Return 404. Clearer for a legitimate client that mistyped an id. It needs an existence check the design has no other reason to run, and it confirms that some tenant owns that id. That is a cross-tenant existence oracle.
17

How do the integration tests avoid consumer-group interference?

Tests
Question asked

The design fixed two test mechanics: a generated keypair and a random tenantId for each run. Slice 4 puts a Kafka consumer inside the application. How do the tests keep the consumers apart?

Why it mattered

Jest runs test files in parallel workers by default. Every integration file would start another consumer in the same group. The group would then rebalance during a test and move partitions between workers. The replay test would become hard to reason about.

Decision

Split Jest into two projects. Unit tests stay parallel. Integration tests run with maxWorkers: 1 and use a random id for the consumer group on each run.

Practical effect

One consumer exists at a time. The committed offsets of a previous run stay out of this run. Unit tests remain parallel and free of infrastructure. One command still runs both projects: nub run test.

Rejected
  • Random group id, keep parallel. Faster. Several consumers then race to index the same documents.
  • Boot one application in global setup. Fastest and fully deterministic. It shares mutable fixture state across test files.
18

How does Message.create read the clock?

Domain
Question asked

Message.create generates a UUIDv7, which embeds a millisecond. It also sets timestamp from the server clock. Two clock reads can straddle a millisecond. How is the clock handled?

Why it mattered

ADR-0013 justifies the _id tiebreaker partly because a v7 id is broadly chronological. That argument depends on the id and the timestamp agreeing.

Decision

Read Date.now() once. Derive the v7 id and the timestamp from that one value.

static create(props: CreateProps): Message {
  const now = Date.now();
  return new Message(uuidV7(now), new Date(now), /* … */);
}
Practical effect

The millisecond inside the id always equals the exposed timestamp. Tests get determinism from Jest fake timers. A unit test now asserts the agreement.

Rejected
  • Inject a Clock port. The textbook-pure answer, and trivially testable. It is a port with no invariant behind it, which ADR-0016 forbids.
  • Two reads, accept the skew. The sort stays a total order either way. The id and the timestamp can then disagree by one millisecond.
19

What produces the explain() result?

Tests
Question asked

The design stated that explain() shows an IXSCAN with no SORT stage, and that the output goes in the README. What produces that result?

Why it mattered

A pasted plan is true on the day someone pastes it. A later change to the index or the sort would then degrade the query in silence.

Decision

Assert the plan in an integration test. Add a nub run db:explain script that prints the same plan for the README. 

const plan = await collection.find(keysetFilter)
  .sort({ timestamp: -1, _id: -1 }).explain('queryPlanner');
expect(stages(plan)).toContain('IXSCAN');
expect(stages(plan)).not.toContain('SORT');
Practical effect

A change to the index or the sort now fails the build. The claim in the README stays true after the commit that made it.

Rejected
  • A script only. Less to write. Nothing stops the plan from regressing.

Glossary

Message
A single utterance stored in a conversation. It is the unit of work of this system.
Conversation
The ordered stream of messages that share a conversationId. It is identified, not stored.
Tenant
The isolation boundary. Every message belongs to exactly one tenant. No read and no write may cross tenants.
Sender
The authenticated principal that created a message, taken from the token's sub claim.
Primary store
MongoDB. It is the single system of record.
Search index
The Elasticsearch representation of messages. It is a derived read model, and MongoDB can rebuild it.
MessageView
A plain immutable type with no behaviour. Read ports return it in place of the entity.
IdentityContext
The domain port that returns { tenantId, senderId }. It throws when the context is absent.
Store
The AsyncLocalStorage value that holds the identity for one request.
Keyset cursor
An opaque value that encodes timestamp, id and direction. The query resumes after that position.
Envelope
The object that wraps a list response, such as { items, nextCursor }.
Poison message
An event that fails every retry. It halts the consumer, because this system has no dead-letter queue.
Slice
One vertical unit of build work. Each slice ends with green tests, a green lint and exactly one commit.
